What I built

Five modules, one AI Associate PM

Each module added one piece. Together they define what the AI does, what it is allowed to do, and what good looks like.

Module 1
Skill file
Role

You are Juno, an Associate PM embedded in a product team. You work across the team's connected tools (for example Linear, Notion, Zentrik, Fireflies, and Teams) to help PMs keep track of documentation that is scattered across them. You support PMs; you do not own product decisions. You read, connect, and summarize. You never create, edit, delete, or send anything in any tool on your own, and you never set priorities or make commitments on the team's behalf.

Task

Given an initiative name, check Notion, Linear, Zentrik, and Teams against the team's documentation standard, then synthesize what each tool says into a single, current picture the PM can act on. Use the initiative name as the key that connects the tools. For every requirement in the standard, report whether it is Met, Not met, Not found, or Can't verify, with the source that proves it. Also surface name mismatches, conflicts between tools, and stale items. Every statement must trace back to a specific source.

Module 2
Prototype
Prototype

What it demonstrates

The assumption the prototype tests is that the initiative name is a reliable enough key to connect Notion, Linear, Zentrik and Teams, so one name can produce a single picture a PM can act on without opening each tool.

Debrief

What broke

Stale items are not a first-class concept. Your task asks Juno to surface stale items, but the prototype only catches one by accident. The L5 gap (latest Pulse is 13 days before the end of the reporting week) is labeled Not found. Other old dates, like the Intent Canvas last edited 2026-10-08, are shown but never flagged. You need a staleness rule (for example, an age threshold per source type) and a visible Stale label.
Conflicts between tools are untested. None of the three scenarios has two tools disagreeing. The Teams mention is deliberately context only, so it doesn’t count. The “synthesize across tools” part of the task has no scenario that exercises it.
Traceability is incomplete. Scorecard rows name their evidence, but the bottom-line sentence, the gap bullets, the open questions and the confidence reason don’t point to a specific source. That falls short of “every statement must trace back to a source.” The scorecard links are also placeholders, so nothing is clickable yet.

What held up (by design, not by test)

Separating Not met, Not found and Can’t verify, so a tool failure never reads as a failure of the initiative.
Treating the name match as a flagged, unconfirmed dependency that lowers confidence (the Appointment Reminders v2 case).
Showing Above range as a count rather than a failure.

Still unknown

Whether a PM accepts a flagged “Near” name match, or needs to confirm it before trusting anything below it.
Whether the four result states are enough to decide what to do next, especially with five unverifiable rows.
Whether the surfaced gaps and questions help or add noise.

Module 3
AI PRD
Problem and user

User: The PMs on your team (Collin, Ron, Emily, Alanna, Sharmila, Andrew, Tim, Alyssa), with you as the person who owns the standard and reads the results. A PM triggers Juno on their initiatives. You see the rolled-up state across the team.

Problem: Each initiative’s documentation is spread across Notion, Linear, Zentrik, Fireflies and Teams, and keeping it consistent is manual. PMs skip it or do it unevenly, so you can’t tell whether an initiative meets the team standard without checking five tools by hand. Asking PMs to do more standardization isn’t working, so Juno needs to do it for them: find the gaps, create the missing matching records, and report only what needs a human decision.

Permissions

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | auto (additive creates only); confirm for edits to existing PM-owned records; blocked for deletes, renames, status/date changes, Intent Canvas edits |
| send | confirm |

Justification:
- read: auto. Changes nothing, so no blast radius and nothing to recover. Asking would defeat Juno's purpose.
- draft: auto. Stays inside Juno's own output until someone acts on it. Worst case is a bad draft that gets ignored.
- write: auto for additive creates only (a missing Linear or Zentrik initiative with the exact Notion name, Juno's own ledger). Blast radius is one new record in one system, easy to spot, easy to delete, and verified by re-read right after. Writes that touch records a PM already owns (milestones, transcript attachments, linking existing records) are confirm, since a wrong change is harder to notice and looks authoritative. Deletes, renames, status or date changes, and Intent Canvas edits are blocked because they can't be reliably undone and are the PM's judgment calls.
- send: confirm. A message to a person can't be recalled and goes out under a PM's name or reaches people outside the initiative. Recovery means a follow-up apology. Confirming costs one click.

Module 4
Agent control panel
What it is doing

Flag the data integrity risk by alert PMs to data inconsistencies in Notion, Linear, and Zentrik.

Rules of engagement

Agency Permission:

Agent can score compliance checks and make mechanical, reversible fixes at High confidence. Agent can draft milestones and Intent Canvas content as “proposed.” Agent CANNOT delete, prioritize, commit dates for a PM, or write on a Near match.

Access Control:

READ: PDDS Initiatives DB (Notion), all Linear teams, all Zentrik teams. WRITE: initiative shells, status, and cross-tool links only. CANNOT delete, edit existing Canvas content, or reach any other system.

Fallback Protocols:

After 1 retry on a tool error, mark checks “Can’t verify” and escalate with full trace. Near or no name match stops all writes. After 2 failures in a run, drop to read-only and hand back to the PM.

Checkpoints:

Dry-run first: PM approves before any write. Milestones, dates, and Canvas content require PM approval. Any Near name match, source conflict, or edit to an existing record goes to PM review.

Module 5
Human eval rubric
What I score

Juno’s initiative sync: when a PM creates an initiative in Notion, Juno creates the matching Linear and Zentrik initiatives and reports what’s missing.. Keep every initiative set up to the team standard across Notion, Linear, and Zentrik without the PM standardizing it by hand, and tell the PM exactly what’s still missing.

Pass bar

Both yes/no questions pass, and the average is 4 or higher on each scale question (gap flagging, edge-case judgment, ready without edits).

Fails outright, whatever the average:

- Consistency: any "no"
- Faithfulness: any "no"
- Juno creating or reporting a record that doesn’t exist in any source, or creating a duplicate initiative without telling the PM.

Module 6

How I’ll know it’s working

The goal the AI is meant to move, where it stands today, and the result that would make me stop.

The goal

When a PM creates an initiative in Notion, the matching Linear and Zentrik initiatives exist within a day, with the same name, without the PM doing anything.

Baseline

Take every active initiative and check each against the standard. Your actual count is the baseline. If you don’t have one, use a rough estimate and label it as an estimate (e.g., “about 50%, to be confirmed by a manual audit before launch”).

Target and review date

90% of active initiatives meeting the standard within 8 weeks of rollout.

Usage metric

% of new Notion initiatives where Juno’s auto-created Linear and Zentrik records were kept as-is, not deleted or recreated by the PM.

Pattern I’ll watch for first

PMs deleting or renaming Juno’s records. That would mean it’s creating clutter or wrong names, so you’d be saving no work and might be adding some.

Stop line

If fewer than 60% of Juno’s auto-created records are kept by the review date, or if PMs spend more time fixing records than they did creating them by hand, stop using it.

Reflection

What I learned

Where it was hardest, what I’ll keep doing, and the moment my thinking changed.

Friction

Friction

The hardest part was holding the big picture while working through the pieces.
We spent a lot of time building skill files in GitHub, and I could see how each
piece worked, but I couldn't see how they fit together into something that runs.
I came in assuming that anything we built would automatically pass through our
harness, our prototype, and our agents. Working through the harness for Juno
showed me that this isn't true. A skill file says what an agent should do. The
harness is what limits what it can see, do, remember, and ship, and it only
applies to work that is deliberately routed through it. Skill files in a
repository don't enforce anything on their own.

The gap for me was execution. I understood the six surfaces (context, tools,
loop, memory, permissions, verification) well enough to design them for Juno,
but I would have liked to see how a design becomes something that runs: where
the harness lives, what connects to it, and what makes sure everything goes
through it instead of around it. My Juno harness is still a design on
demo data, so that last step is where I'd most like more guidance.

Key learnings

Key learnings

What I'll keep doing after the course is working with the templates we now
have. I found them useful because they break a big, fuzzy idea into pieces I
can fill in and check, like the six surfaces of the harness (context, tools,
loop, memory, permissions, verification). I plan to keep using them on real
projects, starting with Juno, so I understand how they work in practice and
how to execute on them, not only how to design with them. Using them on live
work is how I expect to close the gap I described under Friction, between
having the design and having something that runs.

Aha moment

Main aha moment

This class was great for me because I had been seeing and hearing the buzzwords
without a way to connect them. Now I have a solid foundation to continue my path
in AI learning. [Optional: The moment that made it click was the idea that the
model is rented capability and the harness is owned capability. Deciding what the
AI can see, what it can do without asking, and how we check it was right is a PM
decision, and I can make it.]
